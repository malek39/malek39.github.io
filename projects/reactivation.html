A/B Testing Framework.

End-to-end framework for safely running A/B tests at Heetch — turning business asks into statistically valid, interpretable experiments. Covers cohort design, power analysis, MDE trade-offs, deterministic randomization, balance validation, pre-registered analysis plans, and automated Looker readouts. Used across CRM, Acquisition, and Product experiments.

The problem

At a high-growth tech company, experimentation is everywhere — CRM campaigns, acquisition variants, product changes, pricing levers. But running a test is easy; running one that produces a statistically valid, interpretable, and actionable result is hard. The common failure modes are predictable:

  • Underpowered tests. Teams launch with sample sizes that can't detect anything smaller than a moonshot effect, then conclude "no significant impact" when the test was set up to fail.
  • Treatment-heavy splits. "Let's put 90% in treatment because we want to learn faster" — actually inflates variance and requires more sample, not less.
  • Post-hoc analysis. Slicing the data after the fact until something looks significant. Trades discipline for false positives.
  • Non-deterministic randomization. Re-randomization mid-experiment silently breaks reproducibility.
  • No balance check. Treatment and control aren't comparable on pre-experiment covariates, so the effect estimate is biased before it starts.

I built the framework to make all of these failures impossible by construction — not just discouraged by documentation, but blocked by the process itself.

The framework

Six stages, each with a concrete artefact. Skipping a stage isn't a shortcut — it's a red flag that gets caught in review.

1. Translate the business ask into a hypothesis

Every test starts with a single sentence: "We believe X will cause Y, measured by Z." If the team can't write that sentence, the test isn't ready. This forces explicit choice of primary metric and primary unit of analysis (passenger? driver? trip? region?) before any data work happens.

2. Power analysis & MDE trade-off

Given the eligible population size, the historical baseline, and the desired statistical power, compute the Minimum Detectable Effect (MDE). Frame it as a trade-off matrix:

# Smaller MDE → larger sample → longer experiment For a population of 14,000 users with baseline 15%: · MDE 1pp (16% in treatment) → need 28,000 users → infeasible · MDE 2pp → need 7,200 users → feasible · MDE 3pp → need 3,300 users → feasible, faster

This conversation happens with the stakeholder before launch. It forces them to answer: "Is a 2pp effect worth detecting? If not, what is?" Tests that can't detect an effect worth caring about don't get launched.

3. Split optimization — why not 90/10

Stakeholders often ask for treatment-heavy splits ("more learning"). The variance of the difference in means is minimized at 50/50, and any deviation inflates variance proportionally to 1 / (4 × p × (1 - p)):

# Variance-inflation factor relative to 50/50 def vif(p): return 1 / (4 * p * (1 - p)) vif(0.5) # = 1.00 (optimal) vif(0.6) # = 1.04 (+4% sample needed) vif(0.7) # = 1.19 (+19% sample) vif(0.8) # = 1.56 (+56% sample) vif(0.9) # = 2.78 (+178% sample for same power)

The framework documents this so stakeholders see the cost of non-50/50 splits explicitly. We often end up at 60/40 — the sweet spot between statistical efficiency and acceptable treatment volume — but only after the conversation.

4. Deterministic hash-based randomization

All randomization uses a deterministic hash function:

# Reproducible. Immune to re-randomization mid-experiment. treatment = (HASH(user_id || experiment_id) % 100) < SPLIT_PCT

The user always lands in the same arm if the experiment is re-run, which is critical for reproducibility and protects against silent accidental re-randomization when the cohort is regenerated mid-flight. Cohort pipelines are versioned and run against both BigQuery (Eixample) and Redshift (Gotico) where cross-system populations are needed.

5. Balance check & pre-registration

Before launch:

  • Balance check across pre-experiment covariates (historical activity, region, payment method, tenure, segment). Any imbalance > tolerance blocks launch.
  • Pre-registered analysis plan documenting: primary hypothesis, primary metric, secondary metrics with explicit ordering, multiple-testing corrections, exclusion criteria, pre-specified subgroup analyses, and documented caveats.

Pre-registration isn't bureaucracy — it's self-defense against the human tendency to find significance after the fact. Once written, the analysis is locked. Any deviation is documented as exploratory and labelled as such in the readout.

6. Automated readouts in Looker

Result interpretation runs automatically:

  • Primary metric: effect estimate, confidence interval, p-value, practical significance vs MDE.
  • Secondary metrics: same, with multiple-testing correction applied.
  • Balance verification post-launch (did randomization hold up?).
  • Sample ratio mismatch (SRM) test — catches silent randomization bugs.
  • Pre-specified subgroup breakdowns only — no on-the-fly slicing.

Product teams can read the dashboard and reach the right conclusion without a data scientist in the room. That's the test of whether the framework works.

Worked example: Algeria driver reactivation

A concrete application: an Algeria driver reactivation experiment that came through the framework end-to-end.

  • Hypothesis. A reactivation CRM campaign will increase the 14-day reactivation rate of dormant drivers in Algeria.
  • Eligibility. Drivers active in Gotico (Redshift) before the January 2026 migration who had not taken a ride in Eixample (BigQuery) after migration. Built via cross-system anti-join: ~13,870 eligible drivers.
  • Power analysis. Given baseline reactivation and the cohort size, we were powered for MDE ≈ 2pp at 80% power, α = 0.05.
  • Split. CRM initially wanted 90/10. After walking through variance-inflation, we landed on 60/40 — adequate treatment volume without the 178% sample-size penalty.
  • Randomization. treatment = (HASH(driver_id || exp_id) % 100) < 60.
  • Balance check. Confirmed across historical ride volume, days since last ride, sub-region, payment method, registration vintage.
  • Pre-registered plan. 8-section notebook: configuration, helpers, cohort extraction, baseline & power, randomization, balance, export, analysis plan with documented caveats.

The notebook is now used as the senior-level template by the rest of the data team for any supply or demand-side experiment.

Statistical rigour is a kindness to the team — pre-registration protects the business from chasing noise, and a clean experimental design protects the methodology from political pressure.
